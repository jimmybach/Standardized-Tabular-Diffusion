# 第三阶段原生 Windows V2 协议

英文原文：[PHASE_3_V2_WINDOWS_PROTOCOL.md](PHASE_3_V2_WINDOWS_PROTOCOL.md)

- 协议：`pipeline-v2-native-windows-v1`
- 计划：[`pipeline-v2-windows-v1.json`](../../configs/validation/pipeline-v2-windows-v1.json)
- 主要环境：原生 Windows 11 x86-64 与 Python 3.11
- 状态：已完成；18 个计划内适配器全部通过，唯一外部阻塞保持明确

## 1. 目的与结论边界

V2 只回答一个范围严格的问题：第二阶段修复后，当前适配器能否在主要 Windows 环境中，通过权威算法真实完成一次拟合和两次生成？它不评估全量数据质量、原生等价性、榜单资格、Official Results 准入或发布支持。

TabDDPM 和 TabDiff 已拥有更强的 Windows 代表性真实证据。TabEBM 仍受外部条件阻塞，因为真实生成需要受限的 TabPFN-v2 访问权。因此，本阶段安排其余 18 个适配器。

## 2. 真实数据验证夹具

协议从经过审阅且校验和锁定的 UCI Adult 模型视图中，确定性选取 256 个训练行和 128 个测试行。选择先覆盖源切分中观察到的每个类别值，再使用固定种子填充。CSV 与模型原生 NumPy 视图使用完全相同的行索引。清单会记录源哈希、选择索引哈希、输出哈希和计划身份。

这是从 Adult 派生的真实数据验证夹具，不是新的榜单数据集，也不能代替全量 Adult 执行。有界夹具的唯一作用，是让每个可用适配器都能完成一次不可省略的权威真实执行。

## 3. 执行设计

对每个已安排模型，协议会：

1. 强制要求原生 Windows、Python 3.11、已跟踪工作树干净、`pip check` 通过（或仅出现下文已审阅并在计划中精确声明的旧元数据冲突）、声明的依赖锁和请求的 CPU/CUDA 设备；
2. 使用训练种子 `13` 真实拟合一次；
3. 将训练产物按字节复制到两个独立声明的采样工作区；
4. 从完全相同的 checkpoint 字节中，使用种子 `17` 和 `29` 真实生成；
5. 要求精确行数、规范列顺序、无缺失或非有限值、有效类别域、已声明整数列保持整数、两个种子输出不同，且 checkpoint 未被修改；
6. 将第一张有效表路由到中央 `p3-validity` 评测，并验证最终 Result Bundle；
7. 保留命令输入、配置与锁文件哈希、适配器及来源身份、环境、耗时、产物清单、输出哈希、评测 bundle 身份、失败与结论边界。

仅支持 CPU 的算法保持使用 CPU。锁定到已验证 PyTorch 2.3 运行时的模型也保持使用 CPU，因为该运行时早于 RTX 5080 支持。运行时兼容且支持 CUDA 的适配器请求已声明的 RTX 5080。设备选择是保留证据的一部分，由适配器和运行时契约决定，而不会仅根据硬件可用性自动推断。

Goggle 不再绑定旧版 CPU 批次。固定校验的 GCN 核心现在使用单独记录的纯 PyTorch 图兼容后端，因此 Windows V2 profile 会在没有 DGL 和 PyTorch Geometric 的情况下，使用 PyTorch 2.8.0+cu128 与声明的 RTX 5080 运行。DGL 1.1.3 只保留为 Linux 验证判定器，不属于 V2 运行时依赖。

冻结的 CoDi、STaSy 和 TabSyn 快照会导入 `libzero==0.0.8`。该发行包的旧元数据声明 `torch<2`，但精确的新运行时已经通过保留的原生等价工作流。因此，计划只允许完整指定的 `libzero 0.0.8` 与 `torch 2.8.0+cu128` 这一条诊断。执行器会核对已安装版本，要求该豁免恰好实际出现一次，将其写入证据，并拒绝任何变化、新增、无法识别或未实际触发的豁免。

GReaT 使用官方支持的 `distilgpt2` 骨干，在全部 256 行验证数据上训练 5 轮，并以温度 `0.2` 调用官方引导采样。此前的 `sshleifer/tiny-gpt2` 机械烟雾配置能够完成训练，但旧式采样无法产生可解析行，引导采样仍会产生缺失的数值字段。这个小型固件仍适合验证适配器机械行为，但不能视为具备最低 Adult 生成功能。V2 替换只改变公开记录的模型超参数，继续调用未修改的 `be-great==0.0.14` API。

TabuLa 在 Windows 上通过一次性子进程对未修改的方法作者重试循环施加硬超时。只有子进程在声明时限内成功退出，且响应结构、CSV 形状和 SHA-256 完全一致时，父进程才接受输出。超时子进程会被终止，复制的训练制品不会被修改。

TabuLa V2 配置使用官方随机初始化的 `distilgpt2` 结构，在全部 256 行验证数据上训练 20 轮，并使用温度 `0.2`。此前的极小单轮配置能够训练，但进入官方无界重试循环后无法产生可用 Adult 行；新的 Windows 子进程边界在 60 秒诊断时限到达时准确终止了该尝试。接受的配置只调整公开声明的训练强度，没有修改上游源码或采样方程。

## 4. 成本受控批次

| 批次 | 模型 |
|---|---|
| 快速 CPU | ARF、BN、SMOTE、NRGBoost、TabSDS |
| 旧版/运行时锁定 CPU | NFlow、CTAB-GAN、CTAB-GAN+、REaLTabFormer |
| 神经网络 GPU | CTGAN、TVAE、CoDi、Goggle、STaSy、TabSyn |
| LLM GPU | GReaT、TabuLa |
| 重型 GPU | TabularARGN |

失败尝试必须保留并诊断；不得因结果不理想而静默删除或替换。环境修复可以重试，但必须明确保留尝试继承关系。任何算法或配置变更都需要新的协议身份或经审阅的计划更新。

## 5. 验收规则

只有当拟合、两次指定种子生成、结构检查、checkpoint 不可变检查、中央评测和 Result Bundle 验证都在同一已提交适配器版本上通过时，适配器才能成为 `minimal-real-passed`。某个模型的 V2 结果可以验证适用的第二阶段问题，但不会自动提升注册表生命周期等级。

只有当 18 个已安排适配器全部通过、两份既有代表性真实记录仍有效、TabEBM 的外部阻塞仍可独立处理、汇总证据中 21 个身份每个恰好出现一次，且中英文审计文档一致时，本阶段才算完成。

## 6. 完成记录

18 个计划内适配器现均已保留 `minimal-real-passed` 证据。此前的 TabDDPM 与 TabDiff 代表性真实记录继续有效，TabEBM 仍是唯一受外部条件阻塞的身份。汇总审计恰好包含全部 21 个已注册身份，且计划内待测项为 0。此前保留的首次失败、模型专属边界和注册表生命周期边界均不改变。详见[汇总审计](PIPELINE_REAL_FUNCTION_AUDIT.zh-CN.md)及其[机器可读快照](../../configs/validation/pipeline-real-function-audit-v1.json)。
