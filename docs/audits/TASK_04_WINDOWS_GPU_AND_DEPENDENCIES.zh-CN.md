# T04：Windows、GPU 与依赖边界

英文原文：[TASK_04_WINDOWS_GPU_AND_DEPENDENCIES.md](TASK_04_WINDOWS_GPU_AND_DEPENDENCIES.md)

- 状态：进行中；已保留 8 个原生 Windows V2 通过证据，其中包含 NRGBoost 诊断源码构建路径和未修改的 TabSDS 方法作者源码路径
- 上级方案：[跨 Baseline 流水线真实功能审计](PIPELINE_REAL_FUNCTION_AUDIT.zh-CN.md)

## 目标

证明每个受支持适配器能够在主要 Windows/Python 3.11 环境中，使用请求的设备和声明的依赖完成运行。Linux 等价证据仍然有价值，但不能代替这项平台检查。

## 每个适配器的 V0/V1 检查

- 开始工作前解析并记录 Python、软件包、CUDA runtime、PyTorch/TensorFlow、GPU、驱动以及权威源码/包身份。
- 在不移动仓库、也不把源码复制到简化路径的前提下，测试包含空格和非 ASCII 字符的路径。
- 验证 Windows 子进程参数引用、UTF-8 输入输出、路径分隔符、临时目录和进程树终止。
- 验证无界面绘图和可选诊断不会让已经成功的科学计算整体失败。
- 明确请求设备。如果要求或请求 CUDA，意外退回 CPU 必须报错，不能无声改变成本或行为。
- 区分“导入适配器”“训练/生成”“评测”各自需要的包。缺少 extra 时，必须在昂贵运行开始前给出可操作错误。
- 验证兼容桥足够小；涉及源码时应绑定校验和；它必须记录在运行元数据中，且不能改变模型数学逻辑。
- 确认确定性、编码、CUDA 或模块解析环境变量只作用于子运行，不会污染全局环境。

## V2 最小真实探针

在声明的 Windows/Python 3.11 环境运行权威算法，并记录实际软硬件身份。探针必须：

- 确认模型张量和主要计算使用请求的设备；
- 直接从当前包含非 ASCII 字符的仓库路径完成；
- 生成可读的 UTF-8 日志和有效解码输出；
- 执行需要的已批准运行时兼容桥，并保留其标识符；
- 在一次故意设置边界的失败测试中终止完整进程树。

只能使用 CPU 的算法可以明确声明 CPU。某个算法本来就不存在有意义的 GPU 路径时，不能因此把它记作 CUDA 失败。

## 失败条件

- 请求 CUDA 后无声退回 CPU。
- 只在临时 ASCII 路径测试，从而掩盖 Windows 或非 ASCII 路径问题。
- 非必需导入或绘图在没有协议要求时阻止核心生成。
- 兼容补丁改变科学行为，或未验证精确前置条件就被应用。
- 环境记录写的是“请求值”，而不是“实际观察值”。

## 退出条件

每个未阻塞适配器都有一份原生 Windows V2 实测环境记录，设备行为符合声明策略，并且所有平台兼容桥都有窄范围回归覆盖和明确结论边界。
