## 1. 目的

本方案用于发现模型各自的原生等价测试可能遗漏的公共流水线问题。它检查已注册适配器能否收到用户配置、调用权威算法、隔离每次运行、生成合规的解码表，并在主要 Windows 环境中把该表送入中央评测。

这是运行质量审计方案。这里的审计状态不会替代注册表中的验证等级、榜单赛道或支持等级，也不会自动允许任何模型或结果进入 Official Results。

## 2. 当前清单

运行时注册表目前共有 **21 个 baseline**：

- `arf`、`bn`、`codi`、`ctab-gan`、`ctab-gan-plus`、`ctgan`、`goggle`、`great`、`nflow`、`nrgboost`、`realtabformer`、`smote`、`stasy`、`tabddpm`、`tabdiff`、`tabebm`、`tabsds`、`tabsyn`、`tabula`、`tabularargn` 和 `tvae`。
- 其中 20 个保留了 Linux/Python 3.11 下的 `native-parity-validated` 证据。
- TabEBM 为 `smoke-validated`；完整生成依赖受外部访问限制的 TabPFN-v2。
- TabDDPM 已完成原生 Windows 上 Adult 数据集的代表性真实训练/生成，包含 3 个生成种子和最终化的 P5 bundle。
- TabDiff 已完成原生 Windows 上 Adult 数据集的代表性真实训练/生成，包含 3 个生成种子和最终化的中央 P2/P3 bundle。
- Goggle 和 TabuLa 已分别通过原生 Windows V2 最小真实协议：两个不同生成种子、训练产物不变、解码表严格验收，以及最终化的中央 `p3-validity` bundle。
- 另外 16 个计划内 baseline 尚未通过本次新增的原生 Windows 横向真实功能审计。`pending` 只表示尚未按本方案测试，不表示失败。
- SMOTE 是仅支持分类的传统参考方法，不参与生成模型排名，但它的适配器仍要接受同一套流水线契约审计。

第一阶段已完成全部 84 个 T01-T04 V0/V1 任务/模型审计单元，并确认了 10 个问题：9 个 S1 和 1 个 S2。第二阶段已修复这 10 个问题的根因，并通过全部轻依赖回归测试。V2 现在正逐模型推进；已保留 2 个最小真实通过证据，而覆盖更多模型的问题在全部适用真实探针通过前仍保持 `fixed`。注册表生命周期等级未改变。

## 3. 验证层级与结论边界

| 层级 | 实际执行内容 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| V0：清单/静态检查 | 注册表、源码锁、配置解析和路径检查 | baseline 身份明确，声明的资产内部一致 | 真实运行能力 |
| V1：契约模拟 | 使用受控测试替身执行仓库自己的适配器和流水线逻辑 | 配置、路径、错误、产物和路由符合仓库契约 | 权威模型真的能训练或生成 |
| V2：最小真实运行 | 权威算法在小型有效数据/配置上至少真实训练和生成一次 | 被测路径在原生 Windows 上具备冒烟运行能力 | 完整数据质量、原生等价、榜单资格或发布支持 |
| V3：代表性真实运行 | 经审阅的代表性数据/配置、3 个预先声明的生成种子、解码输出和中央评测 | 对该模型/数据/配置/环境身份提供较强真实功能证据 | 自动进入 Official Results，或推广到其他身份 |
| V4：准入/发布 | 冻结协议，以及模型、数据集、指标、运行、环境、许可和治理的独立决策 | 只能支持这些决策明确批准的结论 | 任何未声明的更广泛结论 |

V1 便宜且有用，但绝不能称为真实运行。按本方案，至少完成 V2 后才能声称具备原生 Windows 运行能力。原生等价是另一条独立问题：它必须和固定版本的上游实现精确比较，不能由 V2 或 V3 推断。

## 4. 控制成本的执行策略

1. 先对全部 21 个适配器执行六类 V0/V1 横向任务；这些检查只读，或只写入隔离的临时目录。
2. 修改公共代码前，先把观察结果写入 [PIPELINE_FINDINGS.zh-CN.md](PIPELINE_FINDINGS.zh-CN.md)。
3. 按根因合并已确认问题。公共流水线缺陷只修一次，并为受影响的适配器类别增加回归测试。
4. 对所有不存在外部阻塞的适配器执行 V2。使用最小有效真实数据和模型专属的快速配置，但不替换权威算法。至少真实训练一次、真实生成一次；如果训练和生成可分离，则复用检查点再执行第二个已声明生成种子，否则执行足以检查种子传递的最小第二次运行。
5. V3 只用于准备发布/上榜的模型、高风险适配器，或 V2 暴露出平台敏感问题的模型。某个 V3 失败也可以成为扩大其他模型覆盖面的依据。
6. 不得只保留结果较好的种子，也不得丢弃失败尝试。必须保留声明的尝试链，并区分“环境修复后重跑”和“科学实验重跑”。

这样无需让每个 baseline 都在 Adult 全量数据上跑 3 个种子，同时又为每个可用适配器保留一次不可省略的真实算法检查。

## 6. 调度与修改规则

不同任务可以并行检查不同适配器，但不能同时修改共享的 runner、配置、预处理、编排或评测模块。先检查并产出问题，再按依赖关系和严重程度依次修复。这样能避免一个任务改变另一个任务正在观察的行为，也能避免产生互相冲突的半成品修复。

建议顺序：

1. 先做 T01 和 T02，因为无声的科学错误比使用不便更严重。
2. 再做 T03 和 T04，因为旧产物和平台/设备漂移会让真实运行失效。
3. 有可信解码样本后执行 T05。
4. 针对 T01-T05 暴露出的每个失败边界执行 T06。

## 7. 每个适配器必须保留的证据

每个完成的适配器条目必须记录：

- 模型 ID、固定的上游版本/包、适配器版本和修改状态；
- 精确命令/配置、数据集或 profile 校验和、请求设备和随机种子；
- 实际 Python、Windows、CUDA、GPU 和依赖版本；
- 进程退出状态、耗时、检查点/输出路径、行列数、结构校验结果和文件哈希；
- 不同已声明种子的输出是否不同，或为何预期它们确定性相同；
- 进入中央评测后，最终 bundle 路径及其校验结果；
- 每次失败尝试、修复过程和回归测试；
- 严格限定在被测身份上的结论边界。

大型运行产物默认继续忽略；只有经过单独证据保留决策后，才提交精简 manifest 或结果记录。

## 8. 完成条件

只有满足以下条件，本轮审计才算完成：

- 21 个适配器全部具有 V0/V1 结果；
- 所有未被外部条件阻塞的适配器都在主要 Windows 环境通过 V2；
- 每个外部阻塞都有明确、可单独处理的说明；
- 每个 S0/S1 问题都已修复并有回归测试，或被正式接受为发布阻塞项；
- 中央评测能够拒绝不合规输出，并能在不使用旧评测器的情况下最终化合规输出；
- 机器可读快照、英文文件和中文翻译相互一致。

审计完成后也不会自动改变注册表状态。任何状态提升都必须单独审阅，并附上相应证据。
